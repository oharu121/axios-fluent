# Development Notes - November 10, 2025

## Summary
Fixed IntelliSense import suggestions by adding proper `exports` field to package.json. This resolves the issue where IDEs were showing messy paths like `@node-modules/../dist/../Axon.js` instead of the clean package name.

## Problem Statement

When installing the package, IntelliSense was showing the wrong import suggestion:

**What users saw (BAD):**
```typescript
import from "@node-modules/../dist/../Axon.js"
```

**What users should see (GOOD):**
```typescript
import from "axios-fluent"
```

### Root Cause
The [package.json](../package.json) was missing the modern `"exports"` field, which explicitly defines how the package should be imported. Without it, IDEs fall back to showing the physical file path from node_modules.

## Solution Implemented

### Added `exports` Field to package.json

**Location**: [package.json:7-13](../package.json#L7-L13)

**Change Applied:**
```json
{
  "name": "axios-fluent",
  "version": "1.1.0",
  "main": "dist/Axon.js",
  "types": "dist/Axon.d.ts",
  "exports": {
    ".": {
      "import": "./dist/Axon.js",
      "require": "./dist/Axon.js",
      "types": "./dist/Axon.d.ts"
    }
  }
}
```

### What This Does

**1. `"exports"` field**
- Modern Node.js standard (introduced in Node 12.7+)
- Explicitly defines what can be imported from the package
- Takes precedence over `"main"` field
- Required for proper IDE IntelliSense

**2. `"."` entry point**
- Defines the main export (root import)
- What users get when they write `import Axon from "axios-fluent"`

**3. Dual module support**
- `"import"`: ESM (ECMAScript modules) - `import Axon from "axios-fluent"`
- `"require"`: CommonJS - `const Axon = require("axios-fluent")`
- Both point to the same file for consistency

**4. `"types"` field**
- Tells TypeScript where to find type definitions
- Ensures proper autocomplete and type checking
- IDE can find `.d.ts` file automatically

## Technical Details

### Why `exports` is Better than Just `main`

**Old approach (main only):**
```json
{
  "main": "dist/Axon.js",
  "types": "dist/Axon.d.ts"
}
```

**Problems:**
- ❌ IDEs may show full file paths in suggestions
- ❌ No explicit control over what can be imported
- ❌ No support for different module systems
- ❌ Less clear intent

**New approach (main + exports):**
```json
{
  "main": "dist/Axon.js",
  "types": "dist/Axon.d.ts",
  "exports": {
    ".": {
      "import": "./dist/Axon.js",
      "require": "./dist/Axon.js",
      "types": "./dist/Axon.d.ts"
    }
  }
}
```

**Benefits:**
- ✅ Clean import suggestions in IDEs
- ✅ Explicit module system support
- ✅ Future-proof for package subpaths
- ✅ Modern Node.js standard

### Backward Compatibility

**Important**: Keeping both `"main"` AND `"exports"` ensures compatibility:

- **Older Node.js** (<12.7): Uses `"main"` field (still works)
- **Modern Node.js** (>=12.7): Uses `"exports"` field (preferred)
- **TypeScript**: Uses `"types"` field (works in both cases)

**Result**: Zero breaking changes - all existing users continue to work.

## Common Issues & Solutions

### Issue 1: Old versions of Node.js

**Problem**: Node.js < 12.7 doesn't support `exports` field

**Solution**: We kept the `main` field for fallback
```json
{
  "main": "dist/Axon.js",  // Fallback for old Node
  "exports": { ... }       // Preferred for modern Node
}
```

### Issue 2: Monorepo with multiple packages

**Problem**: Need to export different files for different imports

**Solution**: Add more exports (future enhancement)
```json
{
  "exports": {
    ".": "./dist/Axon.js",
    "./error": "./dist/AxonError.js",
    "./response": "./dist/AxonResponse.js"
  }
}
```

### Issue 3: TypeScript can't find types

**Problem**: TypeScript shows "Cannot find module 'axios-fluent'"

**Solution**: Ensure `types` field is in both root and exports
```json
{
  "types": "dist/Axon.d.ts",  // Root level
  "exports": {
    ".": {
      "types": "./dist/Axon.d.ts"  // In exports
    }
  }
}
```

## Best Practices

### 1. Always Include Both `main` and `exports`

**Why**: Maximum compatibility
```json
{
  "main": "dist/index.js",     // For old Node.js
  "types": "dist/index.d.ts",  // For TypeScript
  "exports": {                 // For modern Node.js
    ".": {
      "import": "./dist/index.js",
      "require": "./dist/index.js",
      "types": "./dist/index.d.ts"
    }
  }
}
```

### 2. Use Relative Paths in `exports`

**Correct:**
```json
"exports": {
  ".": "./dist/Axon.js"  // ✅ Relative path with ./
}
```

**Incorrect:**
```json
"exports": {
  ".": "dist/Axon.js"    // ❌ Missing ./
}
```

### 3. Match Module Types Correctly

**For CJS (CommonJS):**
```json
{
  "type": "commonjs",  // or omit (default)
  "exports": {
    ".": {
      "require": "./dist/index.js"
    }
  }
}
```

**For ESM (ES Modules):**
```json
{
  "type": "module",
  "exports": {
    ".": {
      "import": "./dist/index.js"
    }
  }
}
```

**For Dual Package (our case):**
```json
{
  "exports": {
    ".": {
      "import": "./dist/index.js",
      "require": "./dist/index.js"
    }
  }
}
```

## Lessons Learned

**Wrong:**
```json

  ".": "dist/Axon.js"    // ❌ - Won't work!
}
```

### 4. Backward Compatibility is Critical

**Learning**: Never remove `main` field when adding `exports`

**Reasoning:**
- Older Node.js versions need it
- Some tools don't support `exports` yet
- Zero cost to keep both

## Simplified AxonError (Session 2)

### Summary
Simplified the `AxonError` class to only expose the 5 essential properties needed for error debugging. Removed unnecessary properties to provide a cleaner, more focused error interface.

### Problem Statement

User feedback indicated that AxonError was exposing too much information:

**Issues with original design:**
1. **`headers` property** - Almost never needed for error handling
2. **`originalError` property** - Creates confusion (two ways to access same data)
3. **API bloat** - Too many properties for typical use cases

**User's desired interface:**
```typescript
catch (error) {
  if (error instanceof AxonError) {
    error.status        // 404
    error.statusText    // 'Not Found'
    error.url           // '/api/users'
    error.method        // 'GET'
    error.responseData  // Error body
  }
}
```

### Decision: Simplify to 5 Essential Properties

**Agreement**: After discussion, we agreed that:
- ✅ These 5 properties cover 99% of error handling use cases
- ✅ Simpler API = easier to remember and use
- ✅ No confusion about which property to access
- ✅ Power users can still catch original AxiosError if needed

### Changes Made

**Location**: [Axon.ts:27-54](../Axon.ts#L27-L54)

**Before:**
```typescript
export class AxonError extends Error {
  public readonly status?: number;
  public readonly statusText?: string;
  public readonly responseData?: any;
  public readonly url?: string;
  public readonly method?: string;
  public readonly headers?: any;           // ❌ REMOVED
  public readonly originalError: AxiosError; // ❌ REMOVED

  constructor(error: AxiosError) {
    super(error.message);
    this.name = 'AxonError';
    this.originalError = error;  // ❌ REMOVED

    if (error.response) {
      this.status = error.response.status;
      this.statusText = error.response.statusText;
      this.responseData = error.response.data;
      this.headers = error.response.headers;  // ❌ REMOVED
    }

    if (error.config) {
      this.url = error.config.url;
      this.method = error.config.method?.toUpperCase();
    }

    if (Error.captureStackTrace) {
      Error.captureStackTrace(this, AxonError);
    }
  }
}
```

**After:**
```typescript
export class AxonError extends Error {
  public readonly status?: number;
  public readonly statusText?: string;
  public readonly responseData?: any;
  public readonly url?: string;
  public readonly method?: string;

  constructor(error: AxiosError) {
    super(error.message);
    this.name = 'AxonError';

    if (error.response) {
      this.status = error.response.status;
      this.statusText = error.response.statusText;
      this.responseData = error.response.data;
    }

    if (error.config) {
      this.url = error.config.url;
      this.method = error.config.method?.toUpperCase();
    }

    if (Error.captureStackTrace) {
      Error.captureStackTrace(this, AxonError);
    }
  }
}
```

### Removed Properties

**1. `headers?: any`**
- **Why removed**: Rarely needed in error handling (< 1% of use cases)
- **Alternative**: Power users can catch original AxiosError if needed
- **Impact**: Cleaner API, less cognitive load

**2. `originalError: AxiosError`**
- **Why removed**: Created confusion (two ways to access same data)
- **Problem**: Users didn't know whether to use `error.status` or `error.originalError.response.status`
- **Defeats purpose**: Wrapping errors is meant to simplify, not expose original
- **Alternative**: Advanced users can catch AxiosError directly before wrapping

### Kept Properties (The Essential 5)

**1. `status?: number`**
- Most important property for error handling
- HTTP status code (404, 500, etc.)
- Used in 99% of error handling scenarios

**2. `statusText?: string`**
- Human-readable status ("Not Found", "Internal Server Error")
- Useful for logging and debugging

**3. `url?: string`**
- Which endpoint failed
- Critical for debugging in production logs

**4. `method?: string`**
- HTTP method (GET, POST, etc.)
- Important context for understanding the error

**5. `responseData?: any`**
- Error response body from server
- Contains error messages, validation errors, etc.
- Essential for understanding what went wrong

### Rationale

**Why this is better:**

1. **Covers 99% of use cases**
   ```typescript
   catch (error) {
     if (error instanceof AxonError) {
       console.log(`${error.method} ${error.url} failed`);
       console.log(`Status: ${error.status} ${error.statusText}`);
       console.log(`Error: ${JSON.stringify(error.responseData)}`);
     }
   }
   ```

2. **No confusion**
   - One property = one piece of information
   - No duplicate ways to access same data
   - Easy to remember

3. **Cleaner API**
   - Less cognitive load
   - Fewer properties to understand
   - More focused interface

4. **Power users not blocked**
   ```typescript
   // If someone really needs headers or full axios error
   try {
     await client.get('/api/users').data();
   } catch (error) {
     if (axios.isAxiosError(error)) {
       // Access full AxiosError
       console.log(error.response.headers);
       console.log(error.config);
       console.log(error.request);
     }
   }
   ```

### Why NOT Add a Debug Option

**Considered**: Adding `Axon.new({ debug: true })` to expose more error info

**Decision**: Not needed because:

1. **Adds complexity**
   - Need to pass debug flag through entire chain
   - Two different error behaviors to document
   - More code to maintain

2. **Power users have alternatives**
   - Can catch original AxiosError
   - Can access full error via axios.isAxiosError()
   - Already have toString() for formatted output

3. **Violates simplicity principle**
   - Debug mode = two APIs to learn
   - Users need to remember to enable it
   - Goes against our goal of simplification

### Usage Examples

**Typical error handling (99% of cases):**
```typescript

  }

```
