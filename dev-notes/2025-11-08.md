# Development Notes - November 8, 2025

## Summary
Implemented **response convenience methods** and **enhanced error handling** to improve developer experience. Added chainable `.data()`, `.status()`, `.headers()`, and `.ok()` methods, plus structured error information via `AxonError` class.

## Problem Statement

Users identified two pain points:
1. **Verbose data extraction**: Always need `response.data` to get actual data
2. **Difficult error debugging**: Axios error structure makes it hard to find status, URL, response body

### Example of the Problem

```typescript
// Pain point 1: Extracting data
const response = await client.get<User[]>('/users');
const users = response.data; // Extra step every time

// Pain point 2: Error debugging
try {
  await client.get('/users');
} catch (error) {
  // Have to dig into error.response.status, error.response.data, etc.
  if (error.response) {
    console.log(error.response.status);
    console.log(error.response.data);
  }
}
```

## Solution Implemented

### Design Decision: Chainable Methods After HTTP Calls

**Approach**: Add convenience methods that can be chained after HTTP methods
**Why**:
- Zero breaking changes (100% backward compatible)
- More intuitive than creating duplicate methods like `getData()`
- Follows modern HTTP client patterns (ky, got, etc.)
- Extensible for future enhancements

### Architecture

```
HTTP Method → AxonResponse Wrapper → Convenience Methods
   ↓              ↓                      ↓
 get()      (Awaitable)            .data()
 post()     (Promise-like)         .status()
 put()      (Then/catch)           .headers()
 etc.                              .ok()
```

## Major Changes

### 1. AxonResponse Class [ADDED]

**Location**: [Axon.ts:86-195](../Axon.ts#L86-L195)

**Purpose**: Wrapper around Axios response that is awaitable AND provides convenience methods

**Key Features**:
- Implements `PromiseLike<AxiosResponse<T>>` for backward compatibility
- Returns full `AxiosResponse` when awaited (existing code works unchanged)
- Provides four convenience methods for common use cases

**Methods**:

```typescript
class AxonResponse<T> {
  // Makes it awaitable - returns full AxiosResponse
  then<TResult1, TResult2>(...)
  catch<TResult>(...)
  finally(...)

  // Convenience methods
  async data(): Promise<T>        // Extract just data
  async status(): Promise<number> // Extract just status code
  async headers(): Promise<any>   // Extract just headers
  async ok(): Promise<boolean>    // Check if status 2xx
}
```

**Implementation Details**:
- Constructor wraps axios promise and handles error wrapping
- `then()` method makes it awaitable via Promise interface
- All convenience methods await the internal promise
- Error handling done in constructor (wraps AxiosError)

**Type Safety**:
- Generic `<T>` flows through all methods
- `data()` returns `Promise<T>` (not wrapped in AxiosResponse)
- Fully compatible with TypeScript's Promise typing

**Location**: [Axon.ts:27-80](../Axon.ts#L27-L80)

**Purpose**: Enhanced error class with convenient property access

**Key Features**:

## Technical Details

### How AxonResponse Works

**Flow Diagram**:
```
1. HTTP method called → Returns AxonResponse immediately
2. User chooses:
   a) await response → Calls then() → Returns AxiosResponse
   b) Call .data() → Awaits promise → Returns just data
   c) Call .status() → Awaits promise → Returns just status
   etc.
```

**Implementation Pattern**:
```typescript
constructor(promise: Promise<AxiosResponse<T>>) {
  // Wrap promise and intercept errors
  this.responsePromise = promise.catch(error => {
    if (axios.isAxiosError(error)) {
      throw new AxonError(error); // Convert to AxonError
    }
    throw error;
  });
}

// Make awaitable
then(...) { return this.responsePromise.then(...); }

// Convenience method
async data(): Promise<T> {
  const response = await this.responsePromise;
  return response.data; // Extract just data
}
```

### Error Wrapping Mechanism

**Automatic Wrapping**:
- Happens in `AxonResponse` constructor
- Catches all Axios errors automatically
- No user code required

**Flow**:
```
Axios throws AxiosError
  ↓
AxonResponse catches in constructor
  ↓
Checks if AxiosError (axios.isAxiosError())
  ↓
Wraps in AxonError
  ↓
Throws AxonError
  ↓
User catches AxonError
```

**Type Safety**:
```typescript
catch (error) {
  if (error instanceof AxonError) {
    // TypeScript knows all properties exist
    error.status // number | undefined
    error.url    // string | undefined
  }
}
```

## Lessons Learned

### Design Decisions

1. **Chainable methods > Duplicate methods**:
   - Better API design
   - More flexible
   - Less code duplication

2. **Wrapper class > Prototype extension**:
   - More maintainable
   - Better type safety
   - No pollution of Promise prototype

3. **Automatic error wrapping > Manual wrapping**:
   - Better DX
   - Less boilerplate
   - Consistent error handling

4. **Backward compatibility is critical**:
   - Enables gradual adoption
   - Reduces upgrade friction
   - Maintains trust

### Implementation Insights

1. **PromiseLike interface is powerful**:
   - Allows custom promise-like objects
   - Maintains await compatibility
   - Full TypeScript support

2. **Error wrapping in constructor is elegant**:
   - Catches all errors automatically
   - No need for try/catch in every method
   - Clean separation of concerns

3. **Generic types flow through wrappers**:
   - TypeScript inference works perfectly
   - No type assertions needed
   - IDE support is excellent

### Why Not Other Approaches?

**❌ Manual axios mocking:**
```typescript
jest.mock('axios');
axios.get.mockResolvedValue({ data: mockUsers });
```
- Brittle - breaks if axios internals change
- Unrealistic - doesn't test actual HTTP behavior
- Hard to maintain

**❌ Real HTTP calls:**
```typescript
await client.get('https://real-api.com/users');
```
- Slow - network latency
- Unreliable - depends on external service
- Not isolated - can't control responses

**⚠️ Jest + axios-mock-adapter:**
```typescript
const mock = new MockAdapter(axios);
mock.onGet('/users').reply(200, mockUsers);
```
- Still mocks axios internals
- Less realistic than MSW
- Jest is slower than Vitest

### Key Decisions & Rationale

**1. Vitest over Jest**
- **Decision**: Use Vitest as test runner
- **Rationale**: Faster, better TypeScript support, modern tooling, active development
- **Trade-off**: Smaller ecosystem vs Jest, but compatible API

**2. MSW over axios mocking**
- **Decision**: Use MSW for HTTP mocking
- **Rationale**: Tests real HTTP behavior, more realistic, future-proof
- **Trade-off**: Slightly more setup, but much better testing

**3. 80% coverage threshold**
- **Decision**: Require 80% coverage (75% for branches)
- **Rationale**: Sweet spot - ensures quality without being too strict
- **Trade-off**: Some edge cases may not be covered, acceptable for library

**4. Multiple test categories**
- **Decision**: Separate unit, integration, and compatibility tests
- **Rationale**: Ensures comprehensive coverage of different aspects
- **Trade-off**: More test files, but better organization

**5. CI integration with coverage**
- **Decision**: Run tests + coverage on every PR
- **Rationale**: Catch issues early, maintain code quality
- **Trade-off**: Slightly longer CI time, worth it for quality

### Lessons Learned

**1. MSW is essential for HTTP client libraries**
- Mocking axios directly is brittle and unrealistic
- Network-level interception catches real issues
- Industry standard for a reason

**2. Vitest is the future of JavaScript testing**
- Significantly faster than Jest
- Better developer experience
- Native TypeScript and ESM support

**3. Test organization matters**
- Separate files for different concerns
- Clear naming conventions
- Descriptive test names

**4. Coverage thresholds enforce quality**
- 80% is achievable and meaningful
- Forces thinking about edge cases
- Prevents regression

**5. Good documentation is critical**
- Multiple docs for different needs (quick start, comprehensive guide, technical)
- Examples are essential
- CI/CD integration needs clear explanation
